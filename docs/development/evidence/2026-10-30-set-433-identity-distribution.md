## 2. Remote repository reference and revision identity

`packages/core/src/remote-repository-reference.ts` parses a trimmed `github:owner/repo[.git]` restricted ASCII shorthand; produces lowercase `github:owner/repo` canonical identity and case-preserving HTTPS fetch URL. HTTPS/SSH URL uses WHATWG URL parsing, requires a host and nonempty decoded pathname, rejects password and HTTPS username, query, fragment and decoded `..`; leading slashes and a case-sensitive trailing `.git` strip. SCP matches `user@host:path` with no whitespace, trims leading slash, strips case-sensitive `.git`, rejects empty path or `..`, and retains absolute versus relative semantics in non-GitHub SSH canonical identity. Host canonicalizes lower case; non-GitHub path preserves case. Exact two-component github.com canonicalization merges shorthand, HTTPS and SSH and lowercases owner/repo, while retaining the original fetch URL. This is D2 canonical key construction with D4 server-specific transport identity; it is not a universal guarantee that all SSH users, URL encodings, URLs with encoded reserved characters, path case, `.GIT`, or host-specific rules denote the same authority/resource. SCP and URL branches have different accepted syntax (SCP does not apply URL query/fragment parsing). URL parsing/percent decoding also matters; explicit host/path negative tests are not a full semantic equivalence matrix.

`remote-repository-cache.ts:resolveRemoteRepositoryCache/acquireRemoteRepository` keys by canonical repository and revision kind/value; checkout verification reparses stored origin against canonical, with owned lock and safe publish, then fetches configured stored origin. `config.ts` validates remote entries; `marketplace-check.ts`, `render-marketplaces.ts` canonicalize remote identity for comparison/output; cache is also used in remote acquisition. Revision validators accept `default`, lowercase full 40-hex SHA, semver `version`, or `ref` regex with explicit `..`, `//`, final dot/slash and `.lock` rejection; revision values remain distinct cache keys. `remote-repository-cache.test.ts` covers common GitHub, credentials, file rejection, ports, SCP absolute/relative, cache identity, origin mismatch and cache fencing. `docs/reference/features/marketplaces.md:47,73` describes distinct Claude remote acquisition and Codex catalog Git-source domains: the latter's additional local/file accepted forms must not be generalized to this remote cache parser. D5 invalid inputs fail; D4 encoded-reserved path and accepted scp edge equivalence need either contract narrowing or source-specific evidence before treating aliases as exact; no concrete different repository collision or unsafe effect was demonstrated in this audit.

## Subsequent correction: bind acquisition to the fetch URL

The previously unproven alias concern was reproduced with two disposable Git origins and explicit Git URL rewriting: distinct fetch URLs sharing a canonical display identity could reuse the wrong checkout. Draft [#804](https://github.com/outfitter-dev/skillset/pull/804), final `ae36f64b`, fixes that D6 acquisition boundary. Cache identity hashes the parsed fetch URL, and existing caches must have an exactly matching stored origin. Known-checkout lookup reads the local origin (`git config --local`) and compares the literal URL, so ambient configuration cannot supply a false local match. A mismatch falls back to remote acquisition.

Tests cover five alias pairs in both acquisition orders, tampered origins, literal shorthand origins and ambient config overrides; shorthand and its identical expanded HTTPS URL still share. The broader canonical name remains a display/comparison representation, not acquisition authority. Existing caches are retained; equivalent spellings may become colder. Offline SHA availability does not establish current remote reachability or membership. Both review rounds completed; final full verification recorded 4,515 passes and three deferred native-size failures. Server-specific alias equivalence remains D4; no universal URL-equivalence policy was introduced.
