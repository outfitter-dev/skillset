# ADR: Declarative User-Scope Config

Status: design. SET-560 owns implementation evidence. This record remains a
draft until user-scope discovery, rendering, locking, and reversal are proved.

## Context

People need one place to declare the skills and packages they want available
across repositories. Treating that place as another workspace duplicates the
repository source topology and turns an XDG data directory into hidden authored
truth. It also encourages build, installation, provider discovery, and trust to
collapse into one command.

The source-first boundary still applies at user scope. Authored skill directories
and referenced source locations remain the product. Generated provider copies
are disposable projections, and writing them does not grant provider trust or
edit provider settings.

## Decision

User scope is declarative. Skillset reads one config at the platform's XDG
configuration location, defaulting to
`$XDG_CONFIG_HOME/skillset/config.yaml` with the normal home-relative XDG
fallback. The config lists source directories and package selections; it is not
itself a source workspace and does not contain provider settings or trust.

The default authored user directory is flat:

```text
~/.skillset/
  skills/
    <skill>/
      SKILL.md
```

`~/.skillset/skills/` contributes standalone user skills. Additional declared
sources may contribute skills or selectable plugin packages under their own
ownership. User-scope resolution does not crawl arbitrary repositories, infer
sources from provider directories, or fall back to a hidden global workspace.

`skillset sync --user` renders the declared selection into user discovery
locations:

- the standard Agent Skills projection at `~/.agents/skills/<identity>/`;
- Claude user skills at the provider's documented user skill directory;
- Codex user skills at the provider's documented user skill directory; and
- Cursor user skills only where committed registry provenance and the SET-550
  parity fixtures establish the destination.

The operation writes a user-scope lock that records each source identity,
projection path, hash, role, and owning sync. Subsequent syncs may replace or
remove only paths still proven to be owned by that lock. Unmanaged files,
unknown contents, modified generated bytes, and destination collisions fail or
require an explicit reviewed reconciliation; they are never silently deleted.

`sync --user` is an explicit user-runtime write. It previews planned copies and
removals, then applies them atomically. It does not install plugins, publish
packages, edit provider settings, grant trust, or enable marketplaces. Build
continues to mean rendering into configured project destinations and never
implies this user-scope operation.

There is no compatibility lookup for a former global workspace and no automatic
migration from earlier layouts. A manually run helper may update known internal
workspaces under the hard-cutover policy in ADR-0033, but it is not product
behavior.

## Consequences

### Positive

- User intent has one declarative config and one ordinary authored skill root.
- Provider user directories contain reproducible copies with inspectable
  ownership rather than becoming source truth.
- A user can review one plan and lock across the standard and provider
  projections.

### Tradeoffs

- Sync has user-runtime write authority and therefore needs stronger collision,
  tamper, rollback, and atomicity evidence than a repository build.
- Provider destinations can differ and require registry evidence; an unproved
  destination remains unsupported rather than inferred from another provider.
- Existing experimental global-workspace layouts receive no compatibility
  reader or automatic migration.

### What This Does Not Decide

- Provider trust, activation settings, marketplace enablement, or publication.
- A background daemon, automatic sync, or repository-triggered user mutation.
- User-scope plugin installation beyond explicitly selected skill copies.
- The Cursor destination fixture gap owned by SET-550.
